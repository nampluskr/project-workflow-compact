# DOCUMENTS — 문서 작성 기준

프로젝트마다 쓰는 여섯 문서의 절 구성과 작성 기준을 정한다. 무엇을 어떤 순서로 쓰는지는 [WORKFLOW.md](WORKFLOW.md)에, 문서별 빈 양식은 [templates/](templates/)에 있다.

이 레포의 [specs/v0.1/](../specs/v0.1/)이 이 기준을 따라 쓴 예시다.

## 1. 공통 작성 기준

**항목마다 절을 두고 풀어 쓴다.**
결정 하나, 요구 하나, Phase 하나가 각각 절 하나다. 절 안의 보조 표는 쓸 수 있다. 문서 전체를 표 하나로 요약하지 않는다.

**요구와 결정은 사람이 정한다. 에이전트는 묻는다.**
모르는 것은 지어내지 않고 사람에게 묻는다. 아직 정해지지 않은 것은 "미정"으로 둔다.

**해당 없으면 "없음"이라고 적는다.**
필수 절을 비워 두지 않는다. 비어 있으면 빠뜨린 것인지 없는 것인지 구별되지 않는다.

**근거는 사람의 답과 문서에서 가져오고 출처를 밝힌다.**
"사용자가 골랐다(날짜)"처럼 누가 언제 정했는지, 또는 어느 문서의 어느 항목인지를 적는다. 출처를 댈 수 없는 이유는 쓰지 않는다.

**맨 위 인용 블록은 버전 문서 다섯에 둔다.**
`specs/{version}/`의 INTENT·DECISIONS·SPEC·PLAN·PROGRESS는 맨 위에 인용 블록을 둔다. 첫 줄에 `버전 · 작성일 · 상태`를 적고, 그 아래 한두 줄로 이 문서의 역할과 다른 문서의 위치를 적는다. 루트 INTENT는 버전과 무관하므로 인용 블록을 두지 않는다.

```
> 버전: v0.1 · 작성일: 2026-10-31 · 상태: 초안 (사람 확인 대기)
>
> 이 문서의 역할 한두 줄.
```

**번호는 버전 안에서만 유일하다.**
결정은 `D-1`, 요구는 `R-1`, Phase는 `Phase 1`처럼 매긴다. 다른 문서에서 가리킬 때는 같은 버전의 번호를 쓴다.

**UTF-8로 저장하고 이모지를 쓰지 않는다.**
저장한 뒤 다시 읽어 한글이 깨지지 않았는지 확인한다.

## 2. 문서 관계

문서는 위에서 아래로 좁혀진다. 아래 문서는 위 문서의 의도에 어긋나지 않는다.

1. **루트 INTENT** — 프로젝트가 무엇을 왜 하는가. 버전이 바뀌어도 변하지 않는다.
2. **버전 INTENT** — 이번 버전의 목적과 범위.
3. **DECISIONS** — 이번 버전에서 정한 설계 결정과 그 이유.
4. **SPEC** — 이번 버전이 만족해야 할 요구와 판정 방법.
5. **PLAN** — 요구를 어떤 Phase 순서로 만족시키는가.
6. **PROGRESS** — 실제로 한 일과 검증 결과.

앞의 다섯은 일을 하기 전에 쓰는 문서이고, PROGRESS는 일을 하면서 쓰는 문서다. 새 버전은 `specs/{version}/` 새 폴더에서 시작하고 지난 버전 폴더는 그대로 둔다.

## 3. 루트 INTENT

**위치와 템플릿** — 레포 루트의 `INTENT.md`. 템플릿은 [templates/PROJECT-INTENT.md](templates/PROJECT-INTENT.md)다.

**담는 것**

이 프로젝트가 무엇을 하고, 왜 하며, 어떤 원칙을 지키고, 무엇을 다루지 않는지. 버전이 올라가도 변하지 않는 의도만 담는다. 다른 모든 문서의 기준점이다.

**절 구성**

- `# INTENT — <프로젝트명>`
- `## 무엇을 하는가`
- `## 왜 하는가`
- `## 변하지 않는 원칙`
- `## 다루지 않는 것`

**작성 기준**

짧은 평서문으로 쓴다. 원칙과 다루지 않는 것은 항목마다 한 줄을 쓰고, 필요하면 이유를 한 줄 덧붙인다. 사람이 말한 내용만 쓴다.

**담지 않는 것**

기술·설계·문서 목록·폴더 구조·수치·일정. 버전 줄도 두지 않는다. 그런 것은 버전 문서가 담는다.

## 4. 버전 INTENT

**위치와 템플릿** — `specs/{version}/INTENT.md`. 템플릿은 [templates/INTENT.md](templates/INTENT.md)다.

**담는 것**

이번 버전의 목적과 범위, 끝났을 때 기대하는 결과, 배경, 제외 범위. 루트 INTENT를 이번 버전에 맞게 좁힌 것이다.

**절 구성**

- 맨 위 인용 블록
- `# INTENT — <프로젝트명> <버전>`
- `## 목적·범위·기대 결과` — `목적`, `범위`, `기대 결과` 세 항목을 목록으로 적는다.
- `## 배경` — 이번 버전을 시작하게 된 경위.
- `## 제외 범위` — 이번 버전에서 하지 않는 것을 목록으로 적는다.

**작성 기준**

버전의 의도는 이 파일 한 곳에만 둔다. DECISIONS·SPEC·PLAN·PROGRESS에는 INTENT 절을 따로 두지 않는다. 제외 범위는 "없음"이라고 적는 것과 안 적는 것이 다르다. 없으면 없다고 적는다.

**담지 않는 것**

설계 결정(DECISIONS), 요구와 판정 방법(SPEC), 작업 순서(PLAN).

## 5. DECISIONS

**위치와 템플릿** — `specs/{version}/DECISIONS.md`. 템플릿은 [templates/DECISIONS.md](templates/DECISIONS.md)다.

**담는 것**

이번 버전에서 정한 설계 결정과 그 근거, 검토했지만 고르지 않은 대안.

**절 구성**

- 맨 위 인용 블록
- `# DECISIONS — <프로젝트명> <버전>`
- 결정마다 `## D-n. <결정 한 문장>` 절 하나. 절 안에 소제목 셋을 이 순서로 둔다.
  - `**선택**` — 무엇으로 정했는가.
  - `**근거**` — 왜 그렇게 정했는가. 출처를 밝힌다.
  - `**배제한 대안**` — 무엇을 고르지 않았고 왜 배제했는가. 목록으로 적는다.
- 결정 사이는 `---`로 나눈다.
- 마지막에 `## 미결 사항` — 아직 정하지 않은 것을 목록으로 적는다. 없으면 "없음."

**작성 기준**

결정 제목은 한 문장으로, 무엇으로 정했는지가 드러나게 쓴다. 근거는 사람의 답과 문서에서만 가져온다. 배제한 대안을 적어 두어야 같은 선택지가 다시 올라오지 않는다.

**담지 않는 것**

요구와 판정 방법(SPEC), 작업 순서(PLAN), 실제 진행(PROGRESS).

## 6. SPEC

**위치와 템플릿** — `specs/{version}/SPEC.md`. 템플릿은 [templates/SPEC.md](templates/SPEC.md)다.

**담는 것**

이번 버전이 만족해야 할 것. 요구마다 무엇을 보면 충족됐다고 하는지를 함께 적는다.

**절 구성**

- 맨 위 인용 블록
- `# SPEC — <프로젝트명> <버전>`
- 요구마다 `## R-n. <요구 한 문장>` 절 하나. 절 안에 소제목 넷을 이 순서로 둔다.
  - `**요구**` — 무엇을 요구하는가.
  - `**정해진 결과**` — 만족했을 때 무엇이 어떻게 되어 있는가.
  - `**판정 방법**` — 무엇을 보고 충족을 판정하는가.
  - `**출처**` — 요구의 근거가 된 결정(`D-n`)이나 사람의 답.
- 요구 사이는 `---`로 나눈다.

**작성 기준**

정해진 결과와 판정 방법은 있다/없다로 판정할 수 있게 쓴다. 판정 방법이 없는 요구는 요구가 아니다.

**담지 않는 것**

설계 결정의 이유(DECISIONS), 구현 방법과 Phase 순서(PLAN).

## 7. PLAN

**위치와 템플릿** — `specs/{version}/PLAN.md`. 템플릿은 [templates/PLAN.md](templates/PLAN.md)다.

**담는 것**

요구를 만족시키는 Phase의 순서와, Phase마다 무엇이 되면 끝인지.

**절 구성**

- 맨 위 인용 블록
- `# PLAN — <프로젝트명> <버전>`
- `## 읽는 법과 이 순서에 걸린 규칙` — 번호 표기의 뜻, Phase 순서의 이유, 모든 Phase에 걸리는 규칙.
- Phase마다 `## Phase n — <이름>` 절 하나. 절 안에 소제목 셋을 이 순서로 둔다.
  - `**목적**` — 이 Phase가 무엇을 하는가.
  - `**대응**` — 이 Phase가 만족시키는 요구(`R-n`)와 관련 결정(`D-n`).
  - `**완료 조건**` — 무엇이 되면 이 Phase가 끝인지. 목록으로 적는다.
- Phase 사이는 `---`로 나눈다.

**작성 기준**

완료 조건은 판정할 수 있게 쓴다. 완료 조건이 없는 Phase가 있으면 이 문서는 끝나지 않은 것이다. 모든 요구가 어느 Phase엔가 대응되어야 한다.

**담지 않는 것**

상세 설계(DECISIONS), 문서 본문.

## 8. PROGRESS

**위치와 템플릿** — `specs/{version}/PROGRESS.md`. 템플릿은 [templates/PROGRESS.md](templates/PROGRESS.md)다.

**담는 것**

실제로 한 일과 그 검증 결과. 작업을 끝낼 때마다 쓴다. 계획 밖에서 사람이 요청한 작업도 여기에 남는다.

**절 구성**

- 맨 위 인용 블록
- `# PROGRESS — <프로젝트명> <버전>`
- `## Phase별 진행` — Phase마다 `### Phase n — <이름>` 절 하나. 절 안에 작업마다 한 항목을 적는다. 항목은 `**<작업 이름>** (날짜)` 아래에 `무엇을 했나`, `결과`, `검증`, `특이사항`을 둔다. 특이사항이 없으면 "없음"으로 적는다.
- `## 사용자 요청 작업` — 요청마다 `### <요청 요약> (날짜)` 절 하나. 절 안에 `요청`, `조치`, `결과`, `검증`, `상태`를 둔다. 요청이 없으면 "없음."
- `## 버전 종료` — `사용자 종료 판단`과 `남은 것`. 끝나기 전에는 "진행 중."

**작성 기준**

기존 기록은 지우거나 덮어쓰지 않고 뒤에 더한다. 검증에는 무엇으로 확인했는지를 적는다. 계획 밖 작업은 Phase별 진행이 아니라 사용자 요청 작업에 적는다.

**담지 않는 것**

계획(PLAN), 설계 결정(DECISIONS).
